## Why most of these are worse than they look

A test whose name ends `_is_accepted` / `_is_permissive` / `_is_noop` is
asserting *"this must not raise"*. **That is not an assertion.** If the function
is deleted and its body replaced with `return None`, the test still passes. The
name promises a contract the body never checks.

The sound fix has two parts:

1. **Pin the call actually happened** — `client.get.assert_awaited_once()`. This
   is the load-bearing one: it distinguishes "consulted auth and agreed" from
   "returned early because the code is broken".
2. **Pin the return/post-condition** — `assert await fn(...) is None`.

Doing only (2) is better than nothing and is a one-line change; doing (1) is
what makes the test fail when the behaviour is deleted.

> ### ⚠️ "Assert the return is `None`" is the *weakest* fix available
>
> Any entry below whose recommended fix is only (2) is still a weak test, and
> it should be read as a **floor, not a fix**. `assert fn(...) is None` is
> satisfied by a function whose body was deleted outright and replaced with
> `return None` — which is exactly the regression the test was written to
> catch. It converts a test that proves *nothing* into a test that proves *very
> little*, and it can hide a broken implementation just as effectively as the
> original.
>
> It is worth doing because it removes the false green, and it is a one-line
> change. It is not worth stopping at. Where the recommendation below says
> "same", "minimum sound fix", or "the honest minimum", it means *this is the
> most you can assert without knowing the call was made* — prefer the
> `assert_awaited_once()`-style half wherever a mock or observable state
> exists, and record in the PR which half you did.

## Known limitation of the detector (read before closing the backlog)

**These 61 are a sound floor for the question the tool actually answers — "does
this test's own body reach an assertion?" — and nothing more.** Do not cite the
count as a measure of whether a test can fail. A probe file was written with one
instance of each known blind-spot class and the tool reported **0 findings on
it**. What is and is not covered now:

Detected:

  * no reachable assertion at all (`decorative` / `unasserted`)
  * a bare `except:`, `except Exception:`, **`except AssertionError:`**,
    **`except (AssertionError, ValueError):`**, or **`contextlib.suppress(...)`**
    that can discard the failure (`swallowed`) — the last three were *all*
    missed before; matching on the handler's **name** rather than on the
    exception types **caught** is why
  * an assertion that is present but decided by something else
    (`unfalsifiable`): a bare name compared with itself, an expectation aliased
    from the value under test, and an assertion whose branch already fixed its
    own outcome

Not detected, and documented in the script's `LIMITATIONS` rather than guessed
at:

  * **inverted assertions** — `assert service.thing() is None`, green only when
    production is broken
  * **mock *configuration*** asserted instead of mock *behaviour*
  * **cross-module helpers** — same-module resolution by default; even
    `--follow-imports` only reaches other *test* files, not utility modules
  * **`assert f(x) == f(x)`** — the obvious tautology. An AST-equality rule for
    it was implemented and measured: **20 findings on this repo, every one a
    sound test** (`DatabaseManager() is DatabaseManager()` is a singleton test;
    `create_app() is not create_app()` is a non-caching test), zero defects. So
    it is deliberately not reported.

Also still true: assertions inside a **fixture** are not credited to the test, so
a test whose only check happens in its fixture is reported vacuous.

Every item above was hand-read; the list is accurate, but it is a **lower bound
on reporting**, and it is a complete list of tests whose **own body** contains no
reachable assertion. Closing it will not make "can this test fail?" a closed
question.

Re-run the detector after fixing — the count must go **down**, and
`python scripts/find_vacuous_tests.py --self-test` must stay green. If the count
rises, something has started calling a helper that contains an assertion it did
not use to, and that test should be re-read by hand.
